# [Bug] 跨域控制失败根因分析报告 (RCA)

## 1. 故障现象描述 (What)
- **云端现象**  
  云端下发解锁指令后，因未收到车辆响应触发`TIMEOUT_NO_RESPONSE`错误（req_id: req_8899）  
- **车端现象**  
  T-BOX尝试通过CAN总线发送解锁指令（ID:0x3F2）时，因总线超时导致`CAN TX Timeout`，最终车门未解锁  

## 2. 时序链路还原 (Timeline)
1. `18:51:43.075` 云端通过MQTT下发解锁指令  
2. `18:51:44.075` T-BOX接收并解析指令  
3. `18:51:44.475` T-BOX将指令封装为CAN帧（ID:0x3F2）入队  
4. `18:51:44-49.475` CAN总线持续被ID:0x0C1心跳包占据  
5. `18:51:49.475` T-BOX检测到CAN发送超时（5秒阈值）  
6. `18:51:50.075` 云端因超时终止请求  

## 3. 根因定性 (Why)
**物理层冲突**  
- CAN总线采用非破坏性仲裁机制，ID数值越小优先级越高  
- 发动机控制模块(ECM)异常持续发送高优先级心跳包（ID:0x0C1），导致车门控制指令（ID:0x3F2）始终无法获得总线仲裁权  
- 总线负载率超过90%（正常应<70%），触发T-BOX的CAN控制器保护机制  

**协议解码佐证**  
- ID 0x0C1被解码为`动力总成高优心跳包`（设计优先级最高）  
- ID 0x3F2被解码为`远程解锁指令`（优先级中），需等待总线空闲  

## 4. 责任判定与下一步建议 (Action)
**责任模块**  
- 动力域控制团队（ECM异常心跳问题）  
- 网络通信团队（总线负载监控缺失）  

**修复建议**  
1. **紧急措施**  
   - 对ECM进行强制重启，清除异常心跳状态  
   - 在T-BOX增加CAN总线负载实时监控告警（阈值70%）  

2. **长期改进**  
   - 优化ECM心跳机制：增加心跳间隔动态调整功能（紧急状态可高频，空闲时降低频率）  
   - 车门控制指令升级为`ID:0x2XX`级别（提升仲裁优先级）  
   - 在T-BOX实现CAN消息重试队列（退避算法：50ms/100ms/200ms）
