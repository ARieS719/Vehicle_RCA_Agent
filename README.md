##  1. 为什么要做这个项目？

在日常的实车路测、HIL（硬件在环）测试以及售后排障中，如果遇到类似“远程控车超时”这种故障，查日志往往是一场灾难。

一次失败的控车指令，实际涉及了三个完全隔离的技术栈：
1. **云端（TSP/MQTT）**：记录的是高层 JSON 请求与标准的 ISO8601 时间戳。
2. **车端（T-BOX / Android Logcat）**：记录的是系统中间件状态、网络心跳和毫秒级内核日志。
3. **底盘总线（CAN/LIN）**：底层传输的是高频刷新的十六进制原始报文流（如 `0x3F2`、`0x0C1`）。

**痛点很现实：**
* **时空对齐靠人工**：排障时往往需要同时挂着 MQTT 抓包、ADB 终端和 CANalyzer，靠肉眼去对齐不同工具的时间戳，费时费力。
* **噪音淹没核心错误**：真实的测试日志里充斥着大量的 CPU 监控、Wi-Fi 扫描和常规心跳。真正的报错（Error/Timeout）常常藏在几万行背景噪音的最深处。
* **跨域定责常扯皮**：云端报 `TIMEOUT`，但根因可能是车机网络死锁，也可能是底盘域 ECU 抢占了总线。各团队各执一词，缺乏客观依据。

为了解决这些日常开发中的烦恼，我用 Python 和 LangGraph 写了这个自动化工具。它能够把多源异构日志自动对齐，并借助多智能体（Multi-Agent）和 RAG（检索增强生成），自动输出一份包含时序还原与责任定性的 RCA（根因分析）报告。

##  2. 架构设计与工程取舍 (Architecture & Trade-offs)

在写代码时，我没有盲目追求“全交给大模型搞定”，而是采用了 **“传统确定性工程 + 大模型认知智能”** 的混合架构。

### 为什么不直接把几万行日志喂给大模型？
1. **Token 成本与上下文超载**：实车日志体量很大，无脑上传不仅贵，而且极易触发上下文限制，导致大模型出现“注意力涣散”甚至幻觉。
2. **各司其职**：
   * **时间戳解析、全局排序、正则黑名单降噪**：这些是确定性极高的逻辑，必须由纯 Python 代码以毫秒级精度去硬性保证。
   * **跨域日志关联、语义推理、历史经验比对**：这些属于认知智能，才交由大模型和向量检索来发挥优势。
